# TK-018 — Wybór silnika OCR per run w Run Setup

Status: WYKONANY, niezacommitowany (2026-11-26); zaakceptowany przez użytkownika

## Cel

Operator wybiera silnik OCR przy każdym runie, obok nagrania, profilu i interwału.
Dwa silniki można porównać na tym samym nagraniu jeden po drugim. Dwa runy
nie pracują naraz (decyzja użytkownika, patrz niżej).

## Powód

TK-017 dał wybór silnika tylko w konfiguracji (`DF_OCR_ENGINE`, restart backendu,
jeden silnik dla całej aplikacji). Użytkownik oczekiwał wyboru w aplikacji; wybrał
wariant per run.

## Jeden run naraz — już zagwarantowane

Pracuje jeden run: `uq_pipeline_runs_global_workflow_slot` to unikalny indeks bazy, a
start drugiego runu daje `409 active_run`. Wybór silnika tego nie zmienia i nie
zmienia workera (jeden wątek). Dwa runy na różnych silnikach da się utworzyć
(`queued`), ale pracują po kolei. Poza zakresem: jakakolwiek współbieżność.

## Zakres

1. **Rejestr silników (Access, `access/ocr`).** `OcrEngineRegistry`: `default_id`,
   lista wpisów `{id, name, engine, probe}`, `get(id)`. `composition.py` buduje oba
   adaptery (biblioteka RapidOCR ładuje się dopiero przy pierwszym odczycie, więc
   koszt płaci tylko ten, kto go wybierze). `DF_OCR_ENGINE` zostaje silnikiem
   domyślnym.
2. **Manager.** `create_run(..., ocr_engine: str | None)`: `None` = domyślny, nieznany
   id = `WorkflowError("ocr_engine_unknown")` (400); niedostępny = dotychczasowe
   `ocr_provenance_*`. `describe()` i snapshoty regionów liczone na wybranym silniku.
3. **Worker i wznawianie.** Worker bierze silnik z `run.ocr_engine` (kolumna już istnieje,
   bez migracji), nie z jednego pola. `cancel_current()` idzie do silnika runu w toku.
   Run wstrzymany na jednym silniku wznawia się na tym samym; gdy jego silnik nie jest
   dostępny, kończy się kontrolowanym błędem, nigdy cichą zmianą silnika.
4. **API.** `CreateRunRequest.ocr_engine` (opcjonalne). `system.ocr_engines` w
   `/health` i `/dashboard`: lista `{id, name, available, code, detail,
   uses_text_layout, default}`; `system.ocr` zostaje statusem silnika domyślnego.
5. **UI, Run Setup.** Pole „OCR engine” obok „Source file”, „Profile”, „Sample rate”
   (combobox `GroupedOptionList` w trybie pojedynczym, jak dwa pozostałe).
   Niedostępny silnik jest wyszarzony z powodem z sondy. Domyślnie wybrany silnik
   domyślny.
6. **UI, Profil.** „Text layout” znów zawsze widoczny, z dopiskiem, który silniki go
   używają (Profil nie wie, który silnik przeczyta run). Dopisek składa się z nazw silników
   z `system.ocr_engines`, które mają `uses_text_layout`, np. „Used by: Tesseract.”; frontend
   nie zna nazw silników na sztywno. Wycofuje ukrywanie z TK-017.

## Reguła zmienności (PRAG-08/13) — co ma zostać prawdą

- Tylko `composition.py` zna nazwy konkretnych silników i ich konfigurację. Manager i
  worker znają tylko `OcrEngineRegistry` (kontrakt w `access/ocr/protocol.py`) i
  identyfikatory jako tekst, bez listy wpisanej w kodzie; API nie ma `Literal` z
  nazwami silników, nieznany identyfikator odrzuca Manager przez rejestr.
- Engine (`engines/`) nie dowiaduje się o rejestrze ani o żadnym silniku.
- Frontend czyta listę silników z API; nazwy, dostępność, powód i to, czy silnik używa
  układu tekstu, przychodzą z adapterów (sonda).
- Dodanie trzeciego silnika to nowy adapter, jego sonda i jeden wpis w `composition.py`;
  zero zmian w Managerze, workerze, API i frontendzie. Test to pilnuje: rejestr z
  atrapą silnika o nowym identyfikatorze przechodzi cały przepływ runu.

## Poza zakresem

Współbieżne runy; wybór silnika per region; zmiana silnika istniejącego runu; bramka
jakości RapidOCR (TD-027).

## Design Plan (UI) — do uzupełnienia przy implementacji

Elementy: etykieta pola z ikoną, combobox z listą silników, tekst powodu przy
niedostępnym silniku, dopisek przy „Text layout” w Profilu. Reuse: `GroupedOptionList`,
`Icon`, istniejące style `.df-run-setup__picker` / `.df-run-setup__label`. Wytyczne
(moduły do przeczytania w całości przy planie w `log.md`): GRID-08/10, SPACING-01..13,
FONTSIZE-08/09, COLOR-07/08, OPACITY-02 (stan wyłączony). Brak nowych tokenów.

## Ryzyka do zmierzenia

- Sondy obu silników działają przy każdym odpytaniu statusu. Sonda RapidOCR liczy SHA-256
  ok. 47 MB (dwa modele i biblioteka) bez pamięci podręcznej, tak jak sonda Tesseracta
  liczy swoje pliki. Przy odpytywaniu co 1–2 s w trakcie runu to widoczny koszt CPU;
  wspólna pamięć podręczna pomiaru (po rozmiarze i czasie modyfikacji) dla sondy i
  adaptera.
- Dwa adaptery w pamięci naraz: RapidOCR ładuje modele dopiero przy pierwszym użyciu.
- Testy zakładające jeden silnik w `composition` (atrapy `ocr_engine=` w testach)
  przejdą na rejestr z jednym wpisem.
