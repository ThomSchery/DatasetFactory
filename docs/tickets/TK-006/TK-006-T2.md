# TK-006-T2 — Restart, resume i pełna ścieżka review w E2E

Status: W TOKU — otwarty FIX1 po zimnym review

## Cel

Udowodnić pionowy przepływ w warunkach, których dzisiejszy E2E nie dotyka:
wymuszony restart backendu w trakcie runu, wznowienie bez duplikatów, wszystkie
operacje weryfikacji oraz kontrolowane ścieżki błędu.

## Zależności

TK-006-T1 (`check.ps1` jest bramką tego ticketu). Stoi na infrastrukturze
dostarczonej przez FE-001-F5: `backend/tests/e2e_server.py` uruchamia prawdziwy
composition root, FastAPI, migracje, SQLite i workspace na `D:`, z realnym
FFmpeg i jedynym stubem `DeterministicE2eOcrEngine`.

## Zakres / poza zakresem

i pełną ścieżkę review, oraz nowy scenariusz negatywny.

Playwrighta, cache przeglądarki na `D:`, launcher realnego backendu,

## Kontrakt

Scenariusz 1 rozszerza istniejący pionowy przepływ do pełnej ścieżki z
`TK-006.md`: health → profil → materiał → run → **wymuszony restart backendu** →
resume → korekta geometrii → usunięcie boksu → ręczny bbox → reject → reopen →
accept → eksport → jawne zamknięcie runu przez CAS.

Dzisiejszy spec kończy weryfikację na samym accept, więc reject, reopen, delete
i ręczny bbox nie mają dziś żadnego pokrycia end-to-end — mają je wyłącznie
testy Vitest z fake clientem.

Scenariusz 2 sprawdza w kontrolowany sposób: brakujące źródło materiału,
`409` przy próbie uruchomienia drugiego runu na aktywnym oraz niedostępny
katalog workspace. Asercje obejmują kod błędu z backendu i copy pokazane
użytkownikowi, nie tylko status HTTP.

## Logika

1. Restart jest prawdziwy: proces backendu zostaje zabity i podniesiony
   ponownie na tej samej bazie i workspace. Nie wolno symulować restartu
   czyszczeniem stanu w kliencie.
2. Po wznowieniu run kontynuuje pracę i nie produkuje duplikatów — liczba
   klatek, anotacji i eksportów po resume musi być asercją, nie obserwacją.
   Rezerwacje i reconcilery mają już pokrycie jednostkowe
   (`test_durable_workflow.py`, `ExportReconciler`, `ReferenceAssetReconciler`);
   tutaj chodzi o dowód, że działa to w realnym procesie.
3. Scenariusz negatywny nie może zostawiać po sobie stanu, który psuje kolejne
   uruchomienie — sprzątanie idzie przez ten sam markerowany leaf runtime, co
   reszta E2E.
4. Zielony przebieg nie może zmieniać śledzonych PNG. Determinizm dowodów
   z FIX4 obowiązuje: plain `npm run e2e` zostawia `git status` czysty.

## Done Criteria

- Wymuszony restart w trakcie runu i wznowienie kończą się poprawnym eksportem,
  bez duplikatów klatek, anotacji ani eksportów — potwierdzone asercjami liczb.
- Scenariusz 1 wykonuje każdą operację weryfikacji v1: korektę geometrii,
  usunięcie, ręczny bbox, reject, reopen i accept.
- Scenariusz 2 pokrywa brak źródła, `409` na aktywnym runie i niedostępny
  workspace, sprawdzając kod błędu i copy.
- Trzy kolejne plain `npm run e2e` bez resetu: zielone, identyczne osiem PNG,
  czysty `git status` po każdym.
- `check.ps1` przechodzi w całości.
- Bez nowych zależności i bez zmian kodu produkcyjnego, chyba że E2E wykryje
  realny błąd — wtedy poprawka jest osobnym commitem z opisem znaleziska.
