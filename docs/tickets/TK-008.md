## Kontrakt

`GET /dashboard` zwraca aktywny projekt i run, liczby klatek według statusu
weryfikacji oraz stan systemu. Błąd `500`. Kształt DTO ustala ten ticket i musi
zostać dopisany do `TECH_PLAN §5` zamiast obecnej prozy.

## Logika

1. Aktywny projekt i profil pochodzą z istniejących repozytoriów; brak profilu
   to poprawny stan, nie błąd.
2. Aktywny run to ten w statusie nonterminal; gdy go nie ma, pole jest puste.
3. Liczby klatek według `review_status` liczone jednym zapytaniem agregującym,
   nie trzema stronicowanymi wywołaniami listy.
4. Stan systemu korzysta z `SystemStatusAccess`, tego samego co `/health`; nie
   duplikujemy sond.
5. Ostrzeżenie o `experimental` i `quality_gate` aktywnego OCR jest wystawione
   tak samo jak w `GET /runs/{id}` — dashboard nie może go pomijać.
6. Endpoint jest tylko do odczytu i nie dotyka `review_revision` ani stanu runu.

## Done Criteria

- Test kontraktu: kształt odpowiedzi zgodny z DTO dopisanym do `§5`.
- Test pustego stanu: brak projektu, brak profilu i brak aktywnego runu dają
  poprawną odpowiedź, nie `500`.
- Test liczb: klatki `pending`, `accepted` i `rejected` policzone poprawnie po
  serii decyzji, w tym po `reopen`.
- Test, że ostrzeżenie o eksperymentalnym OCR jest obecne.
- `test_composition` i `test_api_boundaries` zielone dla nowego routera.
- `TECH_PLAN §5` opisuje realny kształt odpowiedzi, nie prozę.
- Pełne bramki backendu zielone: ruff, mypy strict, cały pytest.
