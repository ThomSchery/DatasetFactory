## Cel

Dokończyć wartość produktu: użytkownik może poprawić/usunąć propozycję OCR,
zaakceptować lub odrzucić klatkę, a zaakceptowany stan eksportuje się do COCO.

## Pakiety

Bez biblioteki COCO wymaganej w runtime; dokument generowany przez czysty engine
i walidowany testami/schema fixture. Jeśli dodany validator dev-only, zweryfikuj
utrzymanie/licencję/podatności i nie uzależniaj engine od filesystemu.

## Kontrakt

Implementuje frame detail/image, PATCH/DELETE annotation, POST frame review,
POST/GET export z `TECH_PLAN §5`; wszystkie mutacje wymagają `expected_version`.

## Logika

1. Engine review przyjmuje immutable snapshot; klasa musi należeć do profilu.
2. Delete ustawia stan/tombstone, nie usuwa provenance OCR; zaakceptowana klatka
   jest zablokowana przed mutacją bez jawnego ponownego otwarcia (poza v1).
3. Accept wymaga co najmniej jednej aktywnej, poprawnej anotacji; reject wyklucza całość.
4. COCO pobiera spójny `input_revision`, tylko accepted frames/annotations,
   sortuje deterministycznie i nadaje stabilne numeric IDs.
5. Temp export → walidacja bbox/category/image → atomic rename. Błąd nie publikuje
   częściowego eksportu. Manifest nie zawiera absolutnych ścieżek.

## Done Criteria — Gate 3 backend

- Property/unit tests bbox i przejść review; konflikty version zwracają `409`.
- Nie można przypisać klasy innego profilu, edytować accepted ani eksportować
  pending/rejected/proposed observation.
- Snapshot exportu jest odporny na równoległą zmianę: konflikt revision kończy
  draft kontrolowanym błędem/retry użytkownika, nie mieszanym plikiem.
- Golden COCO fixture ma poprawne `images/categories/annotations`, unikalne ID,
  `[x,y,w,h]`, `area`, `iscrowd=0`; parser/validator otwiera JSON.
- Powtórny eksport tego samego revision jest deterministyczny; brak duplikatów.
- Test path confinement i failure atomowego rename; brak partial published dir.
- API image nie ujawnia arbitrary path; response ma właściwy content type/cache.
- TD-005/006 uzupełnione; wszystkie poprzednie gate'y zielone.
