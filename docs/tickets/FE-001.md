# FE-001 — Pionowy interfejs Home — Impeccable

## Cel

Zbudować desktopowy UI obsługujący pełny przepływ profilu → materiał → run →
weryfikacja → eksport, wierny baseline'owi i bez logiki biznesowej w Client.

## Zależności

FE-SETUP, TK-002, TK-004, TK-005, TK-007. Kontrakty API muszą być stabilne przed
integracją; rysowanie boksów i `reopen` wymagają backendu z TK-007.

## Zakres / poza zakresem

W zakresie: pięć tras/nawigacji, dashboard, profil creation canvas, materiały,
pipeline polling, anotacje canvas/lista, eksporty, stany UI i polski copy.
W zakresie także F09: rysowanie nowego boksu, zmiana geometrii istniejącego i
ponowne otwarcie odrzuconej klatki. Poza: edycja profilu F02, SAM 3 F10, maski,
wieloboki, mobile, dark/light.

## Pliki

- `frontend/src/app/**`, `frontend/src/api/**`
- `frontend/src/features/{dashboard,profiles,materials,annotations,exports}/**`
- `frontend/src/components/common/**` (tylko przez procedurę new-component)
- `frontend/src/styles/**`, testy Vitest/Testing Library i Playwright harness

## Pakiety

React Router, TanStack Query, React Hook Form, Zod oraz istniejący testing stack.
Każdy pakiet: stabilna wersja, official registry, lockfile, audit/licencja. Bez
Zustand, Tailwind, UI kit i canvas frameworka bez udowodnionej potrzeby.

## Kontrakt

Frontend używa wyłącznie endpointów `TECH_PLAN §5` przez jeden typowany client.
Query keys i invalidacje są centralne; polling runu co 2 s tylko w nonterminal
statusach. `runId` żyje w URL; backend jest jedynym źródłem trwałego stanu.

## Logika

1. Powłoka ma dokładnie Dashboard/Profile gier/Materiały/Anotacje/Eksporty oraz
   pięć etapów: Próbkowanie/Regiony HUD/OCR/SAM 3/Weryfikacja; SAM 3 = poza v1.
2. Profil: tekstowa ścieżka reference, podgląd opaque asset, rysowanie regionów
   wyłącznie podczas creation, klasy bazowe i per gra, walidacja inline.
3. Materiał: lokalna ścieżka, profil, interwał; wynik walidacji i start runu.
4. Dashboard/pipeline: query polling, progres, pause/resume/cancel, system status.
   Gdy aktywny OCR ma `experimental=true` lub `quality_gate!=passed`, pokazuje
   stałe ostrzeżenie i nie sugeruje automatycznej poprawności anotacji.
5. Review: stronicowane frames z filtrem po `review_status`, jeden obraz naraz,
   bbox overlay SVG skalowany z naturalnych wymiarów, klasa/confidence/region;
   zmiana klasy, delete, accept, reject oraz reopen odrzuconej klatki.
   Rysowanie nowego boksu i zmiana geometrii istniejącego działają w granicach
   całej klatki, nie tylko wewnątrz regionów HUD. Boks ręczny nie ma confidence
   i jest oznaczony jako `manual`.
6. Eksport: start/status/manifest/output; nie obiecuj train/val ani YOLO.

## Done Criteria — Gate 3 UI

- Każdy element UI ma Design Plan w logu i używa katalogu `new-component.md`.
- Tokeny/kompozycja są wierne Impeccable; teksty polskie, terminy OCR/SAM/HUD bez tłumaczenia.
- Każdy query view ma loading/empty/error/success; mutacje disabled+spinner,
  inline/toast wg FE-06; brak optimistic update dla danych datasetu.
- Canvas bbox zachowuje współrzędne przy resize desktop; test transformacji i hit
  target. Przy <1280 px wyświetla wspierany komunikat, nie ściska edytora.
- Klawiatura/focus/semantyka/kontrast działają; lista anotacji pozwala wykonać
  dostępne v1 operacje bez precyzyjnego klikania bbox.
- Testy interakcji: create profile, import/start, polling transition, 409 version,
  review, export; MSW/fake client nie duplikuje logiki backendu.
- Screenshot QA 1440 px dla pięciu tras i stanów loading/empty/error; 0 unresolved
  CSS vars, brak horizontal overflow ≥1280, brak zewnętrznych font fetchy.
- React components nie wywołują `fetch` bezpośrednio i nie implementują status machine.
- TD-007/010/013 mają uzupełnione lokalizacje.
